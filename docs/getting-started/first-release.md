# 第一次开发

先按[安装说明](installation.md)创建项目并启动服务。真实交付需要模型、GitHub 凭据和可访问的 origin。宿主项目的版本号与 Tracks 自身版本号相互独立；新安装项目从 `v0.1` 或 `v1.0` 开始都会使用完整工作流。

## 提出需求

在 Releases 左侧点击 **+**，选择功能开发，输入一段需求。描述预期使用者、输入输出、成功条件与范围。例如：

> 实现 Python 函数 add(a, b)，输入为整数，返回二者之和；支持正数、负数和零；为公开接口编写单元与集成测试，并提供调用示例。

提交后，Scribe 评估可行性、重复与冲突。选择“立项开发”后，Runtime 创建版本分支和运行；存在活跃运行或未合并版本时，界面会呈现相应的排队或确认结果。

## 参与需求制定

Runtime 依次推进 M-STORY、M-SPEC 和 M-ACC。在当前运行卡片查看需要你作出的决定。从“查看对应文档”进入该阶段的文档，阅读或修改内容，也可在评审期间提交讨论意见。修改会自动保存；遇到并发冲突时，需要选择重载服务器版本或用本地修改覆盖。

文档阅读不会自动返回运行页。点击“返回运行”恢复原运行与所选阶段。Docs 左侧保留各版本的六类文档；尚未生成的设计文档不会凭空出现。

完成三轮需求评审后，M-REQ-APPROVAL 要求人类批准需求基线。批准绑定该版 story/spec/acceptance 的内容摘要。内容变化会使旧批准过期，Runtime 会要求重新确认受影响的内容。

## 让 Runtime 推进开发

批准基线后，Runtime 驱动设计、独立测试和逐任务实现：

1. M-DESIGN：设计文档与宿主执行合同。
2. M-TEST：独立测试、AC 与测试绑定、测试有效性检查。
3. M-IMPL：逐任务的测试、实现、重构、独立评审及全量回归。
4. M-VERIFY / M-SECURITY：冻结候选提交，执行宿主质量、追踪、构建、安装检查、安全检查与 CI 证据回读。
5. M-RELEASE：展示候选、产物和证据，等待人类发布决定。
6. M-PUBLISH / M-MILESTONE：执行宿主合同声明的发布步骤，关闭追踪关系并完成归档。

第一次开发没有历史需求基线，Runtime 会记录真实的初始基线；已有项目使用实际已发布运行的基线。宿主测试合同、质量守卫和当前需求的测试要求仍然必须通过。

进入 M-TEST 前，Runtime 会先执行设计中 `[host-contract]` 声明的环境准备和依赖安装命令。新项目不需要预先借用 Tracks 的开发虚拟环境。准备失败时，运行页会显示错误；中断后续跑会保留同一合同与提交下已成功的步骤。设计变更后重新准备，缺少宿主合同会阻止继续推进。

阶段失败会显示具体原因和建议动作。基础设施问题可在排除后重试；设计或需求不成立时，使用“回退…”选择合法的上游阶段，说明原因后重新规划。Runtime 会使受影响的旧证据失效，再计算新证据。不要手工修改事件数据库来解除门禁。

## 阅读状态和证据

Releases 显示当前阶段、等待人类的动作、阻塞原因、任务进度、阶段内工作流和逐轮执行详情。点击历史阶段可查看过去的执行；当前阶段标记与正在查看的阶段标记相互独立。Todos 聚合等待人类处理的事项。

CLI 可读相同的事件与证据：

```bash
trac status
trac replay <run-id>
trac report --run-id <run-id> --format html
trac check trace --version <product-version> --json
trac check reach --json
```

流程完成应显示 `terminal=released`。`trac run` 返回 0 仅表示本次推进正常停止，可能仍在等待审批或修复。缺少外部凭据和 CI 事实时不会被视为交付完成。

## CLI 入口

也可在已安装项目中从终端提出 story：

```bash
printf '%s\n' '实现整数加法函数，支持正数、负数和零。' | trac start v0.1
trac run
```

终端按阶段使用 `trac triage go --actor <name>`、`trac review no-comment --actor <name>` 和 `trac approve --actor <name>`。Web 服务可以接续同一项目的运行；在 Web 中审批后，后台会继续驱动。查看[运行状态说明](../how-to/inspect-run.md)了解回放与故障证据。
