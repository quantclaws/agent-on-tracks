我体验了许多产品，考察在这些产品中，人与 Agent 如何就文档进行讨论。

在许多产品中，Agent 会帮你写设计文档（也可能是需求文档），然后请求你评论。文档很长，我们的评论往往必须引用到某个段落、某一行，这样讨论的双方才对上下文有一个清晰、共同的认知。

基于 TUI 界面的产品中，这种体验最差，因为你不得不使用行号来引用文档，而行号可能会发生变化。基于图形界面的产品会更好一点。它允许你把光标移动到要讨论的文本处，然后在这里插入一个评论。但是这种方式并没有标准的格式规范，所以一旦在别的 IDE 当中打开，这些讨论就会丢失。而且他们也没有一个允许你进行多轮讨论，和决定讨论是否已经得到了答案的机制。

Agent On Tracks 使用了一种非常巧妙的机制来允许你和多个 Agent 就某行文本进行讨论，它不锁定具体的 IDE，并且自带决定机制。

这种机制被称为 inline-discussion 协议。它基于 Markdown 内置的 block quote 语法进行拓展：

```markdown
line counters 是一个强大的代码行统计工具。

> **Aaron:** 这里的统计是开发语言无关的吗？代码注释是否也计算在内？
>> **Sage:** 语言无关。代码注释也算。@Lex， 你注意这个信息
>>> **Aaron:** 同意，但空白行算吗？
```

如果你常用电子邮件，你会发现，这也是电子邮件中常常用来开启讨论的方式。Agent On Tracks 总是使用那些已被实践验证过的交互方案。

所以，不需要特殊的格式，只需要在原生的 Markdown 和 block quote 语法之上，加上 speaker tag 的扩展即可。它是内联的，所以，讨论天然跟上下文集成在一起。无论对 Agent，还是对人类，这都是让你快速切入讨论的最佳方式。

在上面的示例中，Aaron 是项目Owner(人类)的名字；而 Sage，Lex 则是 Agent 的名字。以这么朴素的方式，就可以让一群 Agent 相互讨论起来。我们准备了相关的 skill (trac-discuz)，但实际上，即使没有定义这个 skill, 我们发现许多 LLM 也能看懂这里有一个讨论正在进行。因为电子邮件是他们训练的语料的一部分，已经早就见过这种语法了。
