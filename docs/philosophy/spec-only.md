# 人类只负责需求

需求是自然语言，实现是程序语言。显然，作为产品的 owner, 你知道你想要什么，也知道如何把它表述出来。至于技术部分，应该由 AI 来负责完成。

Agent On Tracks 可能是第一个以此为设计哲学的框架。

通过 Agent On Tracks，在一次开发中，你只参与到需求评审为止。

为什么这是可能的？

实际上，在纯人类的开发团队中，产品经理通常只负责以自然语言，提出产品的需求。实现则由技术团队完成。一个技术团队通常有项目经理、架构师、开发 lead、测试 lead和若干开发、测试工程师组成。

在 Agent On Tracks 中，Agent On Tracks 运行时担任了项目经理的角色，负责驱动流程顺利运转。子代理 Scribe, Sage, Lex和人类组成需求分析团队。人类提出一个故事种子（可以从一句话开始），Scribe 进行调研，把这个故事种子按照敏捷开发的规范展开完整，把你没有提到、但是是必要的隐含需求也挖掘出来。

在敏捷开发中，故事是最终用户将在什么样的场景下，如何使用某个功能完成什么样的目标的一种叙事。

为了让它能够被实现、被应用、被验收，我们需要把它转换成为规格需求文档（specification 文档）。并且，每一个规格需求都要匹配若干验收标准，这就是 acceptance 文档。

Agent On Tracks 给每一个故事种子、需求项和验收项进行了编号。很显然，这些子项之间不会是孤立的，他们有自己的层次结构和依赖关系。这种结构和依赖提供了进行形式化验证的线索。在后面的设计、具体的开发实现以及测试当中，这些需求项和验收项都会被文档和代码引用，从而形成一个完整的需求分解、跟踪、验收的连锁闭环网络。

当然，在这个网络当中，Agent 的创造力仍然是必须的。但是网络本身就是良好的路径指引，加上 Runtime 在一些关键节点上进行了对齐校验，所以最终即使是智力平平的 Agent 也能够帮助我们实现想要的产品。

这实际上也就是人类开发团队自己的实践。团队里的 Junior Engineer 没有丰富的经验和全局的领域知识，但他们经过培训，懂得如何做好自己分配的一个个小模块。产品经理、项目经理和架构师把一个宏大的任务拆解成一个可跟踪的、指向需求的子任务。Junior Engineer 可以很好地实现子任务，把需求实现成为一个个小的、可组装的模块，最终它们可以组成成为一个宏大的产品。

而现在 Agent 已经足够聪明，他们在几乎所有的技术问题上，都已经超过了人类的架构师、工程师。他们完全可以完成好技术构建的任务，人类需要负责的只有需求 -- 并且不是全部的需求，只是那些标志你的产品和其他人产品差异化的那一小部分需求。
