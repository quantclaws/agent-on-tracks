# v0.9 方向草案：后台持续驱动与 Web 工作台

状态：proposal，2026-09-13。来自Human提出的方向，供制定story/spec/acceptance使用；尚非批准规格或已完成任务。不得以此改写v0.8发布条件。

## 目标与用户故事

作为项目使用者，我通过Web提交story，与需求Agent澄清并确认spec/acceptance后，后台持续推进该run；我不必手动重复执行trac或保持maestro聊天在线。我能随时看到正在做什么、已经验证什么、为什么等待、下一次何时重试以及是否需要我作出决定。

核心收益是运行控制的持久化，而不是多一个命令入口。模型额度不足时服务应可靠等待，到已知恢复时间继续；恢复时间未知时有界退避和探测。后台不会创造模型额度，也不能在停机/无网络时保证瞬时继续。

## 建议架构边界

Web UI → HTTP命令入口 → 持久命令队列/监督器 → 现有Runtime/Executor → agent harness、测试、GitHub与发布effects。

现有append-only事件与状态投影 → 只读查询/事件订阅 → Web UI。

- kernel/Runtime继续决定合法状态转移、RGR、角色隔离和发布权限；server不复制第二套状态机。
- supervisor持有运行生命周期：什么时候调用下一步、等待哪类外部事件、何时重试/续租/恢复。它是确定性的运行控制层，不靠LLM循环猜测下一条命令。
- Agent仍负责需求、设计、实施和独立验收等语义工作。maestro当前承担的工作要拆开：机械推进进入supervisor；设计/修复判断仍由指定Agent处理；产品/风险/发布决策保留可审计的人类入口。
- CLI与Web调用同一应用命令服务，避免两套业务逻辑。初期可由受控worker调用现有CLI过渡，但必须使用结构化命令与结果；不把解析stdout作为长期协议，不从HTTP handler直接运行长任务。
- 沿用项目现有持久事件存储，首先评估最小schema扩展；不预先引入数据库迁移、分布式消息系统或重写Executor。

## 必需工作包与关键验收场景

以下编号为规划包，不是正式FR/AC ID。正式spec冻结时分配稳定ID并逐项关联测试。

| 包 | 必需行为 | 关键验收场景 |
|---|---|---|
| S1 统一命令与查询边界 | CLI/Web共用命令服务；提交返回持久command_id；查询不修改状态 | 相同请求经CLI或HTTP产生等价命令/事件；HTTP超时后重试不会重复执行 |
| S2 持久后台监督器 | 每run单一有效执行者；命令队列、lease及防旧worker写入机制；显式等待原因与下一次唤醒 | 重启server、杀worker、并发启动两个server后不双重dispatch/publish；可重建进行中/等待中命令 |
| S3 等待、额度与恢复 | 区分quota/rate limit/CI/agent/human/不可恢复错误；通知与退避；暂停优先于自动恢复 | 额度恢复后无人工唤醒继续；用户已pause则不继续；服务重启后保留retry_at；未知reset时间不编造倒计时 |
| S4 状态与事件API | 当前投影、事件序号、结构化失败、AC证据链接；支持从游标补读 | UI断线重连补齐事件；事件重复/乱序不使UI倒退；日志可定位到具体run/command/task/AC |
| S5 最小Web工作台 | 项目/run列表，story/需求澄清，进度与证据，等待原因，必要决策 | 完成story→确认需求→自动推进→必要授权→发布/失败可解释的单条真实路径；无需手动输入trac |
| S6 控制与安全边界 | pause/resume、受控cancel、已有escape操作、版本化发布预览决策；本地鉴权、访问范围、秘密脱敏 | pause/cancel与迟到agent结果竞态不越权；stale preview不能批准；HTTP不能提交任意shell；凭据不进入UI日志 |

S1→S2→S3建立最小后台纵向闭环；S4可与S2并行；S5在真实API上构建；S6的接口约束从S1起纳入，集中故障验收最后完成。首个可演示里程碑应是“服务重启后自动续跑一个真实小run”，而不是先完成漂亮的静态页面。

## 人类操作边界

默认只在需求/spec/acceptance确认、真正不可自动化的产品选择、以及当前合同要求的人类发布决定时等待。后台不代替Human伪造approval，不把等待模型额度误报成等待用户。

UI同时显示：工作状态、等待原因、下次动作、已验证AC/仍有缺口AC、最近失败、当前候选及preview是否过期。完成度展示必须源于有依据的项目状态；“测试都绿”与“所有验收子句已闭合”分别展示，不编造百分比。

## 建议首版范围

单用户、本机或受控单实例服务，支持多个项目登记、每run串行执行；并发Agent由现有Runtime控制。UI先覆盖操作与诊断，随后改善体验。事件流可采用单向订阅加命令HTTP接口，具体框架与传输选择在S1接口设计时决定，不为技术选型推迟运行闭环。

不默认纳入：公网多租户、复杂RBAC、团队协同编辑、分布式多节点调度、插件市场、第二语言adapter、通用多registry部署平台、图形化流程编辑器。已延期的架构级安全审查/SCA预检必须在backlog中显式triage，不默认因“后续版本”文字自动变成v0.9承诺。现有docs/status/roadmap只是空骨架，不能据此声称历史延期事项已完整盘点。

v0.8承诺且仍失败的发布功能、AC/RGR证据、宿主真实旅程和质量门不得挪到此版本。v0.9建立在可验证的v0.8 Runtime上，同时允许先并行完成S1/S2设计和独立原型，不能用原型绕过v0.8验收。

## 可靠性与质量要求

- 命令先持久化再执行；进程崩溃后至少一次恢复，effects必须幂等/reconcile，不能承诺外部副作用天然exactly-once。
- 活跃执行租约过期后，新worker拥有新代次；旧worker迟到结果不能继续推动状态或发布。
- server不拥有绕过quality/security/approval的快捷路径。最终副作用仍由Runtime持有。
- Supervisor与UI状态来自同一事件/投影；不维护只在内存中的“运行中”事实。
- 正式acceptance按ID关联可执行测试；保留实施/验收责任分离、RED→GREEN及角色访问隔离。
- 覆盖正常流程、重启、断网、额度不足、多次请求、并发worker、UI重连、迟到结果及人工pause等恢复测试；延迟/资源/并发目标在spec中明确测量口径。

## v0.9 规格阶段需要锁定的决策

推荐首版默认本机单用户，不做公网开放；先由后台包装同一命令服务，保留CLI。进一步确定：服务如何安装/自启、空闲和轮询上限、可同时活动的run数量、发布确认如何提醒、模型额度信号由哪个harness提供。上述可在需求澄清期一次性确认，不能变成开发过程中反复让用户手动驱动。

完成定义：用户提交并确认一个小需求后关闭浏览器；经过至少一次服务/worker重启、一次外部等待再恢复，系统仍推进到明确终态或真正必要的人类决策；重新打开UI可解释全部过程，并可从AC追到测试与候选证据。

## 30 FR 约束下的完整 story 范围（2026-09-13 增补）

建议28条有效FR，保留2条给规格评审发现的真实遗漏。以下P01–P28只是规划序号，正式FR ID需按项目注册分配。不能通过把无关功能塞进同一条FR或把功能伪装成NFR规避上限。30条FR不等于30个任务/30个AC，每条FR按可观察行为拆若干AC。

| 序号 | 候选FR | 本版必须交付的可观察行为 |
|---|---|---|

| P02 | 项目登记与选择 | 在许可范围登记已有仓库、选择项目；显示所属仓库/版本，防止对错误项目执行操作 |
| P03 | 运行环境就绪检查 | 显示合同、harness/model、凭据引用及必需工具是否就绪，未就绪给出原因；沿用已配置环境，首版不做通用包管理GUI |
| P04 | Feature story创建 | UI输入story、版本并创建feature run；失败/重复提交有明确结果 |
| P05 | 两类hotfix入口 | UI选择post-release/dev、issue与目标上下文；复用现有前检，不满足前提不创建假run |

| P10 | 全阶段自动推进 | 非人工等待边界由后台持续推进既有开发、RGR、验证、发布和收尾流程，不需用户反复点击run |
| P11 | 外部等待与重试 | 区分CI、Agent、网络及不可重试故障，按持久条件恢复；无进展不热循环 |
| P12 | 额度等待与续跑 | 可用配额信号决定等待/恢复，已知reset时间持久保存；未知时间有界探测且如实显示 |
| P13 | 崩溃重启恢复 | server/worker重启后找回命令与等待状态；未完成effects按既有WAL/reconcile恢复，不重复发布 |
| P14 | Run列表与总览 | 查看当前/历史run、版本、状态及需要人工处理的数量 |
| P15 | 阶段与任务进度 | 展示当前阶段、任务、已完成/剩余与质量状态；进度依据明确，不把测试数当需求完成率 |
| P16 | Agent执行状态 | 展示角色、任务、正在执行/等待/失败，及可用的执行日志关联 |
| P17 | AC及验证证据视图 | 从AC追到测试node、实际结果、候选与相关证据，标明缺失/过期/未审阅 |
| P18 | 事件与失败诊断 | 可读时间线、错误、重试次数、阻断原因与下一步；日志有项目/run/command关联 |
| P19 | 实时状态与重连 | 在线增量更新；浏览器断线后按游标补读，快照/事件一致，不漏失或倒退 |
| P20 | 人工待办中心 | 集中展示当前合法且必须人工处理的决定、理由及上下文；quota/CI等待不冒充人工待办 |
| P21 | 阶段批准与修订决定 | 原合同要求的非发布审批可在UI完成；操作者、审阅revision、决定可审计，过期审批拒绝 |
| P22 | 发布预览与三择一 | UI审阅当前preview，release/delay/return绑定其digest；必须人工批准的release不可后台代批 |
| P23 | 暂停与继续 | 接收持久pause/resume；显示请求/生效状态；pause优先于自动唤醒，保留已完成工作 |
| P24 | 失败后的受控重试 | 条件修复后从原合法位置重试；重试不能复活过期证据、绕过质量门或重复副作用 |
| P25 | 阶段回拨 | 选择Runtime允许的上游阶段，查看影响并给出理由/确认；屏障、迟到结果隔离及下游证据stale后重新推进 |
| P26 | 放弃运行 | UI受控abandon/cancel，保留审计与已发生副作用，不把终止包装成成功或假装撤销远端操作 |
| P27 | 人工身份与访问控制 | 首版本机单用户鉴权；批准只能来自认证人工入口，后台/Agent不能冒充人类 |
| P28 | 凭据与信息暴露边界 | 使用受控凭据引用，UI/API/日志不泄露密钥；文件与产物读取限制在授权项目及证据范围 |

分组计数：服务/项目3 + 需求入口4 + 后台驱动6 + 状态视图6 + 人工控制7 + 身份/信息边界2 = 28 FR。

全阶段流程语义、测试/实施分离、FULL/RGR、CI、安全门、发布/归档均明确继承v0.8合同；v0.9新增的是可靠服务化和Web操作出口，不按每个既有阶段重写一组FR。功能正确性/所有权/审批约束不可藏进性能NFR；另写明确的性能、资源、测试与覆盖率NFR，不用它们规避功能数上限。

## 一条完整 story 的发布验收脚本

1. 启动服务，在浏览器登记已配置好的仓库并通过就绪检查，创建feature story。
2. 用户在UI完成必要澄清，审阅spec/acceptance并作出绑定revision的批准。
3. 关闭浏览器，后台自动走设计→测试→实施/RGR→验证；重新打开后进度和证据连续可读。
4. 注入一次可恢复的外部等待和一次worker/server重启，恢复后无需用户重新执行trac；重复提交命令不会多派发。
5. 在运行中请求pause，观察“已接收→已暂停”；明确resume后才继续。用户请求合法阶段回拨，审阅影响并确认，旧Agent迟到结果不能推进被回拨的流程，下游证据按规则失效并重验。
6. 在所有原合同要求的人工门处可靠等待；用户未批准时不越过。UI过期页面上的批准必须被拒绝。
7. 当前candidate所有门通过后，在UI审阅preview并人工release，后台完成发布与归档；UI能查到真实remote结果及AC证据链。
8. 另外验证post-release/dev两条已有旅程能通过Web入口运行，dev不生成公开release。退出/取消/真实不可恢复错误均有明确终态。

这条纵向验收是story完成条件，不以28个API endpoint存在或页面全部画好作为完成。

## 现有代码的服务化可行性与必须改造点

代码核查基线：8a3b941产品代码（规划提交不影响产品）。以下是源码可见基础与风险，不等于已通过服务化验收。

| 现有基础/问题 | 代码入口 | 迁移安排 |
|---|---|---|
| 已有状态驱动执行循环及pending恢复 | tracks/executor/run_loop.py:run_loop | 重用kernel/Executor；暴露结构化drive结果，区分继续/等待人/等待外部/终态/失败 |
| CLI长循环占用写锁 | tracks/cli/run_cmd.py:cmd_run、tracks/cli/common.py:writer_lock | 单项目worker控制写入；HTTP快速持久受理，worker在边界处理；不能并发调用两个CLI假定可抢占 |
| 人工批准已校验需求revision | tracks/cli/gate_cmd.py:cmd_approve | 抽成共同应用服务，Web显式提交expected revision及认证actor；复用校验而非直接append human.approval |
| release决定已有preview绑定与拒绝过期机制 | tracks/cli/release_cmd.py:cmd_release | Web只适配输入/输出，保留已有authorization校验及不可自动代批的边界 |
| 回拨已有允许目标、不可逆操作确认、escape barrier和证据stale | tracks/cli/gate_cmd.py:cmd_return | UI展示合法目标与影响；worker串行落实屏障；不是直接改state.stage或执行git reset |
| 部分执行上下文为进程内状态 | run_loop恢复failure-review的逻辑 | 首版worker采用进程隔离，审计重启恢复；不能把共享全局变量/同一DB连接直接放进多个HTTP线程 |

建议首版单机单服务，项目写入串行化、项目间可由受控worker进程隔离；避免先做多机分布式锁。命令服务逐步从CLI handler抽出，保持CLI兼容。读取状态不等待长任务结束；数据库连接与读事务独立管理。后台已受理控制命令必须有明确生效边界，长时间不可中断步骤需显示原因并定义超时/终止/恢复策略。

阶段回拨不是撤销历史：已经推送的tag/release不会凭回拨消失。必须列出实际已发生副作用，确认后按现有合同回到允许位置；需要业务补救时另作明确决定。暂停/回拨遇到正在发布的effects，也不能粗暴杀进程后宣称未执行，应读回reconcile。

## 开工前优先证明的技术纵向切片

先做S1/S2的小切片：一个真实worker运行已有run，HTTP能读进度、受理pause、显示pause生效；杀worker后恢复；在合法人工门停住，批准后继续；回拨后旧结果被隔离。同一场景用CLI和Web分别验证。先证明锁、控制与恢复机制，再铺开其余页面。

判断：已有核心机制支持这个演进方向，没有看到必须重写整个项目的证据；当前代码不能视为已经可直接多线程挂载的Web后台。v0.8尚未闭合的功能/真实旅程问题仍须先解决或被明确列为服务化原型的已知前置阻断，不能靠Web页面掩盖。
