## 2. 用户意图

- **用户想完成什么**：把现在需要人工（或 Maestro 保持在线）逐条手动执行的命令串起来，由后台在应该自动推进的地方持续推进：一个 run 从提交 story 走到发布/终态，路径上的澄清、批准、发布与运行控制等人工决定在 Web 界面完成。
- **当前哪里受阻**：v0.8 的每一步推进都要人工逐条执行命令或保持 Maestro 聊天在线；浏览器/终端会话一关，推进即停；外部等待（CI、模型额度、网络）没有持久化的"等一等再继续"，批准与发布决定也没有脱离命令行的 Web 交互面。
- **完成后能看到什么结果**：提交并确认一个小需求后关闭浏览器，系统在后台经设计→测试→实施/RGR→验证自动推进，经过至少一次外部等待与服务/worker 重启仍推进到终态或真正必要的人工决定；重新打开 Web 可解释全部过程（进度、等待原因、AC 证据链），并在 UI 完成批准、发布、暂停/继续、放弃与阶段回拨。

## 3. 核心操作路径

### 3.1. 服务启动、项目登记与就绪检查

- **变更基线**：新增 — 无（新增路径）。v0.8 无服务进程：运行由用户在 CLI/聊天会话中逐条命令驱动（`tracks/cli/run_cmd.py:cmd_run` 长循环占用写锁），不存在可脱离会话独立存活的执行体。
- **入口/触发**：用户在本机（单用户受控实例）启动服务，通过健康检查后打开工作台入口，进入项目登记与就绪检查页面。

1. 用户启动服务并确认健康状态（浏览器打开工作台或健康端点返回可用），服务进程独立于浏览器存活。
2. 用户在许可范围内登记已有仓库/选择项目，界面显示所属仓库与版本，防止对错误项目执行操作。
3. 用户运行就绪检查，查看合同、harness/model、凭据引用与必需工具的就绪状态；未就绪项显示具体原因。

- **完成结果**：项目已登记且就绪状态可见；就绪后用户可继续创建 run；未就绪时显示原因，用户修复后重查（沿用已配置环境，首版不做通用包管理 GUI）。服务可停止/重启，重启后恢复已登记运行状态。

### 3.2. 创建 feature run（含 hotfix 两类入口）

- **变更基线**：修改 — v0.8 中用户在 CLI 输入 story 创建 run 并需手动逐段驱动；本次新增 Web 提交入口，同一命令服务受理，语义与去重沿用现有合同并强化（持久 command_id）。
- **入口/触发**：工作台项目页 → 新建 run；hotfix 经同一入口选择 post-release / dev 类别、issue 与目标上下文。

1. 用户输入 story 内容与版本并提交；失败或重复提交有明确结果（不创建假 run）。
2. 提交返回持久 command_id；刷新/超时重试不会重复创建 run 或重复执行人工决定。
3. 新 run 出现在总览列表，进入待澄清/待推进状态；hotfix 入口复用现有前置检查，前提不满足时给出原因。

- **完成结果**：run 已创建并可追踪；用户可继续澄清，或关闭浏览器等待后台推进。post-release/dev 两条已有旅程均可经 Web 入口运行，dev 不生成公开 release。

### 3.3. 需求澄清、材料审阅与批准

- **变更基线**：修改 — v0.8 人工澄清与批准经 CLI 交互与 approve 命令完成（`tracks/cli/gate_cmd.py:cmd_approve` 已校验需求 revision）；本次改由 Web 界面完成，复用既有校验而非直接 append human.approval。
- **入口/触发**：run 进入澄清/批准等待时，人工待办中心或 run 详情页出现需要回复或批准的事项。

1. 用户阅读 Agent 提问与讨论历史并在 UI 回复；后台续接原 run，不新开无关联会话。
2. 用户审阅 story/spec/acceptance/design 当前版本及变更，确认对象 revision。
3. 用户对绑定 revision 的确认/批准作出决定；系统记录操作者、审阅 revision 与决定，过期 revision 的批准被拒绝。
4. 批准生效后后台自动推进下一阶段（BS-07）。

- **完成结果**：澄清闭环——材料已批准或返回修改，均有审计记录；run 在用户确认后继续自动推进。

### 3.4. 后台自动推进与恢复

- **变更基线**：新增 — 无（新增路径）。v0.8 的"人在场驱动"被本次有意替换：非人工等待边界由持久 supervisor 自动推进，等待与恢复可跨浏览器关闭、服务重启存活。
- **入口/触发**：用户在完成澄清与必要批准后关闭浏览器（或停留在总览）；后台 supervisor 持有 run 生命周期，按既有 Runtime 状态机决定下一步。

1. 关闭浏览器后，supervisor 沿设计→测试→实施/RGR→验证自动推进既有阶段流程；CLI 与 Web 遵守同一仲裁，同一 run 只有单一有效执行者，不双重 dispatch/publish。
2. 遇到 CI/模型额度/网络等外部等待时，系统持久化等待原因与下一次唤醒（retry_at）；可用额度信号决定等待/恢复，未知 reset 时间有界探测、不编造倒计时、无进展不热循环。
3. 服务/worker 重启后，系统找回进行中/等待中的命令与等待状态，未完成 effects 按既有 WAL/reconcile 恢复，不重复发布外部副作用。
4. 非人工门全部通过后，run 停在人工待办中心或进入可发布状态。

- **完成结果**：用户重新打开 UI 即看到 run 已推进到人工门或终态，或正等待（等待原因与下次唤醒如实显示）；无需用户逐条执行 trac。重复提交命令不会多派发。

### 3.5. 状态查看与断线重连

- **变更基线**：修改 — v0.8 状态经 CLI 输出与日志查看；本次提供 Web 只读视图（事件/投影），查询不修改状态，覆盖实时查看与诊断。
- **入口/触发**：工作台总览 → run 详情/时间线；所有查看入口只读。

1. 用户查看 run 总览：当前/历史 run、版本、状态、待人工处理数量、当前阶段与任务、已完成/剩余与质量状态；进度依据明确，测试数与需求完成率分别展示、不编造百分比。
2. 用户从 AC 追到测试 node、实际结果、候选与证据关联，缺失/过期/未审阅项被标明。
3. 用户查看事件时间线、错误、重试次数、阻断原因与下一步；日志可定位到具体 run/command/task/AC（本版不要求展示 Agent 会话内容/视图；run/任务级执行状态展示见 BS-10/BS-12）。
4. 浏览器断线后重连，系统按游标补读事件，快照与事件一致，事件重复/乱序不使 UI 倒退。

- **完成结果**：用户可解释 run 当前状态、卡点与下一步，并跳转到对应操作入口（批准、暂停/继续、放弃、回拨、发布）。

### 3.6. 发布预览与 release 决定

- **变更基线**：修改 — v0.8 release 由 CLI 命令完成（`tracks/cli/release_cmd.py:cmd_release`，已有 preview 绑定、过期拒绝与不可自动代批边界）；本次仅把输入/输出适配到 Web，保留既有 authorization 校验。
- **入口/触发**：run 的 candidate 所有门通过后，进入可发布状态并出现在人工待办中心；用户从待办中心或 run 详情进入预览页。

1. 用户审阅当前 preview（含 digest 与过期状态提示）。
2. 用户选择 release / delay / return 之一，决定绑定该 preview digest；过期 preview 的批准被拒绝。
3. release 经既有 authorization 与发布流程执行，UI 显示真实 remote 结果并可查 AC 证据链。

- **完成结果**：发布完成/延迟/退回均有明确终态与审计记录；必须人工批准的 release 不会被后台代批。发布成功后 run 进入归档/收尾；已推送的 tag/release 不会被回拨抹掉。

### 3.7. 运行控制：暂停/继续、放弃、阶段回拨

- **变更基线**：修改 — v0.8 的 pause/return/abandon 经 CLI 或人工编辑执行；本次提供 Web 受控入口，延续既有合法性校验（`gate_cmd.py:cmd_return` 的允许目标、不可逆操作确认、escape barrier 与证据 stale 规则）。
- **入口/触发**：run 详情页或人工待办中心的控制区；控制命令持久受理，有生效边界。

1. 用户请求 pause：界面显示"已接收→已暂停"，pause 优先于自动唤醒；resume 后从原合法位置继续并保留已完成工作。
2. 用户请求受控 abandon/cancel：系统保留审计与已发生副作用，不把终止包装成成功、不假装撤销远端操作。
3. 用户发起阶段回拨：选择 Runtime 允许的上游阶段，查看将失效的证据与影响并确认；屏障生效后旧 Agent 迟到结果不能推进被回拨的流程，下游证据按规则失效并重验。

- **完成结果**：控制命令生效状态可见，run 停在用户控制的终态或按新决定重新推进；可恢复失败经受控重试从原合法位置继续（BS-19）；退出/取消/真实不可恢复错误均有明确终态。

## 4. 行为种子

### BS-01 服务生命周期独立于浏览器

- EARS: `WHEN 用户启动/重启服务并完成健康检查, THE 系统 SHALL 保持服务存活并恢复已登记的运行状态，浏览器关闭不影响 run 推进`
- 来源: [3.1 / 规划 P01]
- 说明: 保护"运行控制持久化"这一核心收益——服务不是会话的附属品。

### BS-02 项目登记与就绪检查

- EARS: `WHEN 用户在许可范围登记仓库并运行就绪检查, THE 系统 SHALL 显示项目归属（仓库/版本）及合同、harness/model、凭据引用与必需工具的就绪状态和未就绪原因`
- 来源: [3.1 / 规划 P02-P03]
- 说明: 防止对错误项目执行操作，并让"为什么还不能开始"可解释。

### BS-03 创建 run 持久受理与去重

- EARS: `WHEN 用户提交 story 与版本创建 run, THE 系统 SHALL 返回持久 command_id 并创建可追踪的 run；重复提交或刷新重试不重复创建、不重复执行人工决定`
- 来源: [3.2 / 规划 P04、P08]
- 说明: HTTP 超时重试与双击提交不得造成双 run 或重复副作用。

### BS-04 hotfix 入口复用前检

- EARS: `WHEN 用户选择 post-release/dev hotfix 入口, THE 系统 SHALL 复用现有前置检查，前提不满足时不创建假 run 并给出原因`
- 来源: [3.2 / 规划 P05]
- 说明: 两类已有旅程经 Web 进入，但语义与门槛不因新入口放宽。

### BS-05 澄清续接原 run

- EARS: `WHEN 用户在 UI 回复澄清问题, THE 系统 SHALL 记录回复并续接原 run，不新开无关联会话`
- 来源: [3.3 / 规划 P06]
- 说明: 需求澄清是同一 run 生命周期内的交互，不是新的提交。

### BS-06 绑定 revision 的人工批准

- EARS: `WHEN 用户对材料作出批准/确认, THE 系统 SHALL 记录操作者、审阅 revision 与决定，并拒绝基于过期 revision 的批准`
- 来源: [3.3 / 约束 / 规划 P07、P21]
- 说明: 批准只能来自认证人工入口且绑定具体 revision，后台与 Agent 不得冒充人类。

### BS-07 后台自动推进与单一有效执行者

- EARS: `WHEN run 处于非人工等待边界, THE 系统 SHALL 由单一有效执行者沿既有阶段流程自动推进，无需用户逐条执行命令；CLI 与 Web 遵守同一仲裁，不双重 dispatch/publish`
- 来源: [3.4 / 规划 P09-P10]
- 说明: 本 story 的核心偏离"人在场驱动"；单执行者仲裁防止并发推进产生越权状态。

### BS-08 外部等待持久化

- EARS: `WHEN run 等待 CI/模型额度/网络等外部条件, THE 系统 SHALL 持久化等待原因与下一次唤醒并如实显示；未知恢复时间有界探测，不编造倒计时、无进展不热循环`
- 来源: [3.4 / 规划 P11-P12 / Maestro 钉死点：额度信号 spike]
- 说明: 等待是持久状态而非瞬时错误；后台不会创造模型额度，也不能在停机时保证瞬时继续。

### BS-09 崩溃重启恢复

- EARS: `WHEN 服务/worker 重启, THE 系统 SHALL 找回进行中/等待中的命令与等待状态，未完成 effects 按既有 WAL/reconcile 恢复，不重复执行外部副作用`
- 来源: [3.4 / 约束 / 规划 P13]
- 说明: 至少一次恢复 + 幂等/reconcile，崩溃不产生重复发布或丢单。

### BS-10 run 总览与有依据进度

- EARS: `WHEN 用户查看 run 总览/进度, THE 系统 SHALL 显示当前/历史 run、状态、待人工数量、阶段/任务与质量状态，进度源于项目状态，测试数与需求完成率分别展示、不编造百分比`
- 来源: [3.5 / 规划 P14-P15]
- 说明: "测试都绿"与"所有验收子句已闭合"分别呈现，不把测试数当需求完成率。

### BS-11 AC 与证据链

- EARS: `WHEN 用户查看 AC, THE 系统 SHALL 展示从 AC 到测试 node、实际结果、候选与证据的关联，并标明缺失/过期/未审阅`
- 来源: [3.5 / 规划 P17]
- 说明: 证据可追溯是发布/回拨判断的依据，展示必须来自有依据的项目状态。

### BS-12 人工待办与诊断语义

- EARS: `WHEN 用户查看待办或失败诊断, THE 系统 SHALL 只把合法且必须人工处理的决定列为人工待办（quota/CI 等待不冒充），并显示阻断原因、重试次数、下一步及 run/command/task/AC 日志关联`
- 来源: [3.5 / 约束 / 规划 P18、P20]
- 说明: 等待模型额度与等待用户决定必须可区分，不能把两者混为一谈误导用户。

### BS-13 断线重连不倒退

- EARS: `WHEN 浏览器断线后重连, THE 系统 SHALL 按游标补读事件，快照与事件一致，事件重复/乱序不使 UI 倒退`
- 来源: [3.5 / 规划 P19]
- 说明: 实时订阅与历史补全共用同一事件源，用户看到的是单调一致的投影。

### BS-14 发布决定绑定 digest

- EARS: `WHEN 用户在 UI 对 preview 作出 release/delay/return 决定, THE 系统 SHALL 将决定绑定 preview digest，拒绝过期 preview，且 release 只能由认证人工批准、后台不得代批`
- 来源: [3.6 / 约束 / 规划 P22]
- 说明: 发布是不可逆外部副作用，决定必须绑定用户实际审阅过的内容。

### BS-15 pause 优先于自动唤醒

- EARS: `WHEN 用户请求 pause, THE 系统 SHALL 持久化 pause、显示"已接收→已暂停"，并在 resume 前暂停自动推进、保留已完成工作`
- 来源: [3.7 / 规划 P23]
- 说明: 用户对运行节奏拥有最终控制，自动恢复不得越过用户暂停。
